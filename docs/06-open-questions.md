# 미확정 사항

팀에 물어보거나 직접 확인해야 하는 것들. 위로 갈수록 급하다.

---

## Q1. 촬영 대상과 최종 용도 — **가장 급함**

무엇을 담는 건지, 그 데이터가 어디 쓰이는지 모른다. 이게 정해지면 줄줄이 결정된다:

- 영상 화질·프레임레이트 (용량과 배터리에 직결)
- 촬영 화면 세로/가로 — 노면·시설물이면 세로로 충분, 거리 전경이면 가로가 유리
- 대상 범위 (아래 Q2)
- 인도·골목이 포함되는지 → 도로 형상 데이터 출처 (Q4)

## Q2. 대상 범위 — **성동구로 보임 (2026-09-24)**

서버 데이터셋이 `seongdong-walk-2026-09`: 성동구 보행 네트워크 9,529구간, **총 425km**.
양방향·재촬영 없이 한 번씩만 걸어도 수집가 1인당 약 210km — 여전히 크다. 실제 목표 범위는 팀 확인.

성북구 규모로 이야기됐으나 **도보 기준으로는 재산정이 필요하다.**
시속 4km로 300km를 걸으면 인당 40시간 순수 보행이다. 수집가 2명으로는 비현실적.

실제 범위가 좁으면 지도 광역 뷰(동 단위)가 아예 필요 없을 수도 있다.

## Q3. 대상 플랫폼 — **안드로이드로 가닥** (2026-09-23)

팀 답변: "안드로이드로 진행할 것 같다". 이후 팀원이 iOS 지원 가능 여부를 물어 **양쪽 지원 검토 중**.
개발 확인은 iPhone Expo Go로 한다 — 이를 위해 SDK 52 → 57로 올림. iOS를 지원하면 HEVC(H.264 강제)·iCloud 백업 제외가 다시 필요하다. 기종은 아직 모름 — spike는 실제 수집가 폰으로 돌려야 의미가 있으니 확인할 것.

**안드로이드로 가면서 사라진 것:** HEVC 코덱 문제(안드로이드 녹화는 기본 H.264/mp4), iCloud 백업 제외, iOS 빌드(맥+개발자 계정).
**남는 것:** 자이로 기기 편차, 백그라운드 위치 2단계 권한(10+), `react-native-maps`의 Google Maps API 키
(안드로이드 dev build는 키 없으면 지도가 빈 화면).

아래는 결정 전 비교 기록.

**사용자가 3명뿐이므로 그 사람들이 쓰는 기기만 지원하면 된다.**
공식 배포할 앱이 아니라 양쪽을 다 지원할 이유가 없다.

정해지면 사라지는 문제들:

| 안드로이드만 | iOS만 |
|---|---|
| iOS 코덱(HEVC) 문제 없음 | 자이로 편차 없음 |
| iCloud 백업 문제 없음 | 백그라운드 위치 2단계 권한 없음 |
| iOS 빌드 불필요 (맥 + 개발자 계정) | |

기종까지 알면 좋다. 발열·배터리는 기기빨이라 spike를 그 폰으로 돌려야 의미가 있다.

**플랫폼별 차이 정리:**

- **영상 코덱** — iOS는 `.mov` + HEVC 가능성. 브라우저에서 재생이 안 되는 경우가 많아
  검수 웹에 직격이다. 앱에서 H.264 강제 또는 서버 트랜스코딩 필요.
  용량 추정도 달라진다 (HEVC는 H.264의 절반).
- **iCloud 백업** — iOS `documentDirectory`는 기본 백업 대상. 제외 플래그 필요.
- **자이로** — 안드로이드는 기기별 편차가 크다. 저가 모델은 자이로가 없어 자력계로 추정하며
  주변 금속에 영향받는다. 축 규약도 달라 플랫폼별 보정 필요.
- **GPS** — 안드로이드는 fused provider가 Wi-Fi·기지국까지 융합해 궤적이 매끄럽게 나온다.
  `speed` 필드는 iOS가 도플러 기반으로 더 정확. (현재 거리 계산은 `speed`를 안 쓴다)
- **권한** — 안드로이드 10+ 백그라운드 위치 2단계, 13+ 알림 권한 별도.

## Q4. 도로 형상 데이터 출처 — **해결 (2026-09-24)**

서버가 **서울시 도보 네트워크**를 쓰고 있다 (`/roads/summary`). 횡단보도·육교·지하도(`path_type`)까지 포함. 아래는 결정 전 기록.


`RoadTable.geometry`를 어디서 채울 것인가. 네이버 지도 API는 주지 않는다.

- **ITS 표준노드링크** — 공공데이터. 링크 1개 = 교차로~교차로 구간이라 100m 클립과 스케일이 맞고
  `RoadTable`의 구간 단위 요구와 자연스럽게 맞물린다. **단, 차량 도로망이라 인도·골목·계단이 없다.**
- **OSM** — `highway=footway|path|steps|pedestrian` 태그로 보행로가 잘 들어가 있다.
  **도보 수집이므로 이쪽이 유력하다.**

Q1의 답(골목·인도 포함 여부)에 달렸다.

## Q5. 영상 실물 저장 위치

로컬 디스크 / 오브젝트 스토리지(NCP, S3, MinIO) / NAS.

도보라 클립이 길어져 용량이 크다 — 클립당 80~100MB(H.264), 3000개면 270GB.
로컬 디스크로 시작하기엔 빡세다. **720p 하향을 검토할 것** (용량 절반, 배터리에도 도움).

## Q9. 같은 구간 중복 accept를 km로 인정하나 — **팀에 물어볼 것**

두 명이 같은 구간을 찍어 둘 다 accept되면 둘 다 확정 km에 들어가나?
- 둘 다 인정 → 쉬운 길을 중복으로 찍는 유인. 팀 의견은 "돈 더 받자고 일을 늘리진 않을 것".
- 구간당 **첫 accept만** 인정 → 유인 제거. 대신 검수 웹이 중복 여부를 알아야 한다.

메인 화면의 `확정 km` 계산 기준이 이 답에 달렸다. 뷰 작업은 영향 없음.

## Q8. 검수 웹 — **팀원이 구현 (2026-09-23)**

`HYU-WCS/video-collector-web`, 배포 주소 `http://166.104.36.71:8002/video-validator/` (2026-09-30 확인).
원본 todo 항목은 모두 있다: 지도(성동구 보행로 전체, 상태 색) / 대기·완료·미연결 큐 / 지도에서 도로 선택·연결 /
승인·반려(사유 필수)·롤백 / 변경 이력 / 영상 재생 / 궤적 표시.

남은 것:
- **영상 시간 ↔ 지도 위치 연동 없음.** 궤적 조회 API가 선(LineString)만 돌려준다.
  서버는 `offset_ms`를 저장하므로 응답에 넣어 달라고 요청하면 된다.
- GPS 정확도 표시 없음 — 서버가 `acc`를 저장하지 않는다 (docs/04 "실제 백엔드").
- 도로 자동 매칭 없음 — 검수자가 구간을 하나씩 클릭한다.

## Q10. 누운 옛 클립 회전 — **서버에서 처리하자고 요청할 것** (2026-10-04)

**증상:** iPhone에서 가로로 찍었는데 영상이 90° 누운 **세로 파일**로 저장된 클립이 있다 (예: `clip_1790936260305`).

**원인:** iOS `expo-camera`는 녹화 시작 순간의 기기 방향(`UIDevice.orientation`)으로 영상 방향을 정한다.
제어센터 **세로 화면 고정**이 켜져 있으면 가로로 들어도 portrait로 읽힌다.
앱은 `responsiveOrientationWhenOrientationLocked`(가속도계로 방향 판정)로 고쳤다 (`RecordView`).
**이후 클립은 정상**이고, 문제는 이미 찍힌 클립뿐이다.

**지금 앱의 우회 (임시):** 파일이 세로(회전 반영한 첫 프레임 높이 > 너비)면 화면에서만 -90° 돌린다.
- 영상 상세: 플레이어를 돌리면 iOS 기본 컨트롤까지 같이 누워서, 컨트롤을 숨기고 재생/정지·전체화면만 직접 얹었다. **스크럽바가 없다.**
- 앨범: 첫 프레임 jpg를 -90° 돌려 표시.
- 회전 방향(반시계)은 클립 하나로 정한 값이다. 반대쪽 가로로 들고 찍은 클립은 거꾸로 나온다 — 파일만으론 구분 불가.

**서버에 요청할 것:** 업로드 후처리(`processing` 단계)에서 세로 영상을 반시계 90° 돌려 가로로 다시 저장한다.
이미 올라간 영상도 한 번 일괄 처리. 예: `ffmpeg -i in.mp4 -vf transpose=2 -c:a copy out.mp4` (transpose=2 = 반시계 90°).
검수 웹도 같은 파일을 보므로 검수자 화면도 함께 정상이 된다.

**서버가 처리하면 앱에서 걷어낼 것:** `storage.isPortraitVideo`, `useVideoDetail`의 `sideways`,
`VideoDetailView` `Player`의 회전·자체 컨트롤, `useAlbum`의 `thumbSideways`.
단, 폰에 남은 옛 클립의 로컬 jpg는 여전히 세로다 — 앨범 회전은 그 jpg가 사라질 때까지 남겨도 된다.

## 확인 안 된 기술 전제 (spike 필요)

**아직 실기기에서 아무것도 검증하지 않았다.** 아래가 무너지면 설계 일부를 들어내야 한다.

- 카메라 + 지도 + GPS 동시 구동 시 프레임 드랍 / 발열
- **배터리 지속 시간** — 도보는 충전원이 없다. 보조배터리가 장비 전제인지 확인.
- 100m 클립 실제 용량 (코덱 확인 포함)
- 백그라운드 전환 시 녹화 중단 동작
- `expo-camera`에서 코덱·해상도를 어디까지 지정할 수 있는지
- 안드로이드 기기의 `DeviceMotion` pitch 값 안정성
